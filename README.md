# روح — دليل النشر على Netlify + Supabase

## الخطوة 1 — Supabase
1. supabase.com → New Project (اختر منطقة قريبة، مثلاً Frankfurt).
2. بعد إنشاء المشروع: **SQL Editor → New query**، الصق كل محتوى ملف
   `supabase_schema.sql` واضغط **Run**.
3. **Authentication → Providers** → فعّل **Email**.
4. **Project Settings → API** → انسخ:
   - **Project URL**
   - **anon public key**

## الخطوة 2 — تجهيز المشروع محليًا
تحتاج Node.js مثبت على جهازك (node.js.org).

```bash
cd rouh-app
npm install
cp .env.example .env
```

افتح `.env` وحط فيه القيم اللي نسختها من Supabase.

للتجربة محليًا:
```bash
npm run dev
```

## الخطوة 3 — GitHub
```bash
git init
git add .
git commit -m "روح — نسخة أولى"
```
أنشئ مستودع جديد على github.com وارفع الكود إليه (`git remote add origin ...` ثم `git push`).

## الخطوة 4 — Netlify
1. netlify.com → **Add new site → Import an existing project** → اختر المستودع.
2. Build command: `npm run build` (موجود مسبقًا في `netlify.toml`)
3. Publish directory: `dist`
4. **Site settings → Environment variables** → أضف:
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_ANON_KEY`
5. Deploy.

## الخطوة 5 — حسابات الفريق والصلاحيات
1. كل شخص يفتح الرابط يضغط "أنشئ حساب" بإيميله واسمه — يُنشأ له تلقائيًا
   حساب بصلاحية **"موظف"** (نقطة البيع + البيع اليومي فقط).
2. **أول أدمن (سند)**: بعد ما تسجّل حسابك، روح لـ Supabase →
   **SQL Editor** وشغّل (بريدك الفعلي بدل المثال):
   ```sql
   update public.profiles set role = 'admin'
   where id = (select id from auth.users where email = 'sanad@example.com');
   ```
3. من بعدها، سجّل دخول كأدمن وروح لتبويب **"المستخدمون"** — من هناك تقدر
   ترفّع أي حساب لـ "مدير" أو "أدمن" بدون ما ترجع لـ SQL مرة ثانية.

**المستويات الثلاثة:**
- **أدمن**: كل الصفحات + إدارة المستخدمين
- **مدير**: كل الصفحات التشغيلية والمالية (بدون إدارة المستخدمين)
- **موظف**: نقطة البيع والبيع اليومي فقط

## ملاحظات مهمة
- البيانات محفوظة في Supabase (سحابيًا) — تظهر على كل الأجهزة بعد تسجيل الدخول.
- بيانات المتجر (JSON واحد كبير) يقدر يقرأها ويعدّلها أي شخص مسجّل دخول،
  بغض النظر عن صلاحيته — التحكم بالصلاحيات حاليًا على مستوى الواجهة
  (إخفاء التبويبات) وليس على مستوى قاعدة البيانات. مناسب لفريق صغير
  موثوق؛ لو احتجتم فصلًا حقيقيًا على مستوى القاعدة لاحقًا (مثلاً منع
  الموظف من تعديل المصروفات حتى لو تلاعب بالواجهة)، نحتاج إعادة تصميم
  الجداول لتكون منفصلة (كما في مستند ERD السابق) مع سياسات RLS لكل جدول.
- شكل حفظ البيانات حاليًا هو JSON واحد كبير (نفس شكل التطبيق الحالي)
  للسرعة في النقل بدون أخطاء. الترقية لتصميم علاقي كامل (جداول منفصلة
  للمنتجات والفواتير...) موجود مسبقًا كمستند تصميم (ERD) ويمكن تنفيذه
  كخطوة لاحقة عند الحاجة لتقارير أعمق.
